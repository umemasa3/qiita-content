# Qiita記事の書き方

このリポジトリでQiita記事を書く・直すときは、このファイルのルールに従う。
ルールはユーザーの指摘から育てる。指摘を受けたら「学習の手順」に沿ってこのファイルに書き足す。

## 書く前の進め方

- 話の筋はユーザーが決める。いきなり本文を書かず、ネタ・構成・タイトルの案を2〜3個ずつ出して選んでもらう
- 本文の前に事実確認を済ませる。製品の仕様は公式ドキュメントで確かめ、何年何月時点の情報かを本文に書く
- 情報は削る方向で書く。調べたことを全部載せない。記事の結論に効かない情報は落とす
- ただし削りすぎない。製品比較の記事では、各製品の章に仕様の具体（設定名、デフォルト値、注意点）を残してよい。5製品で本文約380行の記事は、ユーザーが多すぎないと判断した

## 中立性

- 複数の製品を比べる記事では、特定の製品を推しているように見せない
- 製品の並び順は、タイトル・タグ・本文・表のすべてでアルファベット順にそろえ、そのことを本文に書く
- 評価が読者の環境で逆転する観点（どの基盤を持っているか、など）には◎○△を付けず、事実だけを並べる
- タグは一部の製品名だけを付けない。製品が多いときは一般的なタグにする

## 避ける書き方

見出し:

- 「先に結論」「まとめると」のような言い回しを使わない。見出しは「結論」「まとめ」のように短く書く

文章:

- 「XではなくY」「XだけでなくY」の対比を続けて使わない
- 動詞を名詞にした言い方（「学びを書く」など）を避け、動詞で書く（「学んだことを書く」）
- 標語のような言い回しを避ける。具体的な値・手順・設定名を書く
- 「〜と言えるでしょう」「〜が鍵です」のような締めの決まり文句を使わない
- ダッシュ（——、—）で文をつながない。句点で文を分ける
- 太字は1つの節で数か所までにする。箇条書きの各行を太字で始めるのは、項目名を示す必要があるときだけにする

## 分量の目安

指摘を受けると反対側へ極端に直りがちなので、上限と下限を決めておく。数値は初期値で、指摘を受けたら直す。

- 1つの段落は2〜4文。表や箇条書きの直前に置く前置きの1文は例外
- 1つの箇条書きは3〜7項目。「2つのレイヤー」のように、対になる2項目を並べるリストは例外
- 1つの節（###）に、表・注記ボックス（:::note）は合わせて2つまで

## リポジトリの決まり

- 記事は `public/` に置く。新規記事のfrontmatterは `id: null`、`updated_at: ""` にする
- 画像は `public/images/` に drawio.svg で置き、`https://github.com/umemasa3/qiita-content/blob/main/public/images/<ファイル名>?raw=true` で参照する
- push前に `npm run lint:md` を通す（1行120文字まで。表は対象外）
- 公開済みの記事を直すときは、必ず最新のmainからブランチを切る。古いブランチから直すと `id` が `null` に戻り、Qiitaに同じ記事がもう1本できる

## 学習の手順

ユーザーに「学習しといて」と言われたら、次の順で進める。

1. そのセッションで受けた指摘を並べる
2. 指摘ごとに、何が原因で不自然だったのかをユーザーと話して特定する（例:「学びを面白く書いていた」は、動詞を名詞にしたのが原因）
3. 原因を1行のルールにして、このファイルの該当する節に書き足す。指摘された文そのものではなく、同じ癖が次に出ないような書き方にする
4. 極端に直りやすいルールには、「分量の目安」に上限と下限を書き足す
5. 書き足した内容をユーザーに見せ、コミットしてよいか確認する
