## はじめに

Red Hat Developer Hub（RHDH）やBackstageをInternal Developer Platform（IDP）として導入する際、Software Templateを使ったセルフサービス化は大きな魅力です。開発者がフォームに入力すれば、インフラのプロビジョニングやアプリケーションの初期構築が自動で行われる。理想的な世界です。

しかし、ミッションクリティカルなシステムを抱える組織では、**すべてを即時実行のセルフサービスにするわけにはいきません。**

- 本番環境への変更には承認が必要
- セキュリティ要件を満たしているかのチェックが必要
- コスト影響の大きいリソース作成は事前確認が必要

つまり、「申請 → **承認** → 実行」というフローが求められるケースが多くあります。

ところが、Backstage/RHDHのScaffolderには、ネイティブの「承認ステップ」が存在しません（2025年現在、[Issue #13809](https://github.com/backstage/backstage/issues/13809)で議論中）。では、どうやって承認を挟むのか？

本記事では、RHDH/Backstageで承認付きワークフローを実現する3つのパターンを紹介し、それぞれの特徴からどのような場合にどのパターンが適しているかを考えます。

## 前提：なぜ「完全セルフサービス」にしないのか

パターンの説明に入る前に、なぜ承認を挟む必要があるのかを整理します。

**完全セルフサービスが適するケース：**

- 開発環境の構築（影響範囲が限定的）
- テンプレートからのリポジトリ作成（元に戻しやすい）
- 個人の検証用リソース作成（コストが小さい）

**承認が必要なケース：**

- 本番環境・共有環境へのリソース追加
- ネットワーク設定やセキュリティグループの変更
- 月額コストが一定以上のリソース作成
- 組織のコンプライアンスポリシーで承認が義務付けられている作業

ミッションクリティカルなシステムを運用する組織では後者のケースが多く、「便利だから全自動で」とはできない現実があります。ただし、**承認が必要 ≠ 手作業が必要** です。承認後の実行は自動化できます。

## パターン1：Scaffolder → Git PR承認 → 自動実行（GitOpsベース）

### 概要

ScaffolderでパラメータをGitリポジトリへのPull Requestとして出力し、共通基盤チームのPRレビュー・Approveを承認行為とするパターンです。

### フロー

![パターン1：GitOps PR承認フロー](https://github.com/umemasa3/qiita-content/blob/main/public/images/rhdh-pattern1-gitops.drawio.svg?raw=true)

### 実装のポイント

- Scaffolderの標準アクション `publish:github:pull-request` を使用するため、カスタムアクションの開発が不要
- GitリポジトリのブランチプロテクションルールとCODEOWNERSで承認者を制御
- PRテンプレートにチェック項目を設けることで、レビュー観点を標準化できる
- CI（GitHub Actions等）でPR作成時にバリデーション（Terraform plan、ポリシーチェック等）を自動実行できる

### メリット

- **導入コストが低い** — 標準アクションだけで実現可能
- **承認の証跡がGitに残る** — 誰が・いつ・何を承認したかが自然に記録される
- **レビュー文化との親和性が高い** — エンジニアにとってPRレビューは馴染みのあるフロー
- **段階的に導入可能** — 一部のテンプレートから始められる

### デメリット

- **非エンジニアの承認者には敷居が高い** — Gitの操作やPRの概念を理解する必要がある
- **承認のSLAが見えにくい** — PRが放置されても気づきにくい（通知設定が別途必要）
- **複数段階の承認に不向き** — 「チームリーダー → セキュリティチーム → インフラチーム」のような多段承認は表現しづらい

### 適するケース

- 承認者がエンジニアである（共通基盤チームが直接レビュー）
- IaCベースの変更管理（Terraform、Kubernetes manifest等）
- 既にGitOpsの文化がある、またはこれから導入する組織

## パターン2：Scaffolder → 外部ワークフローシステム連携

### パターン2の概要

ScaffolderのカスタムアクションからServiceNow、Jira、または社内ワークフローシステムにリクエストを起票し、そのシステム上で承認が行われたらWebhookやAPIで自動実行をトリガーするパターンです。

### パターン2のフロー

![パターン2：外部ワークフローシステム連携](https://github.com/umemasa3/qiita-content/blob/main/public/images/rhdh-pattern2-external-wf.drawio.svg?raw=true)

### パターン2の実装ポイント

- ScaffolderのカスタムアクションとしてAPIコール処理を開発する必要がある
- 外部システムからの承認完了通知（Webhook）を受けて実行するパイプラインの構築が必要
- 承認フローのロジック（誰が承認するか、エスカレーション等）は外部システム側で管理

### パターン2のメリット

- **既存の承認フローを活用できる** — すでにServiceNow等で承認運用がある場合、そのまま乗せられる
- **非エンジニアの承認者に優しい** — ServiceNowやJiraのUIは非技術者にも馴染みがある
- **複雑な承認ルールに対応** — 多段承認、条件分岐、SLA管理、エスカレーションが外部システムの機能で実現可能
- **監査・コンプライアンス対応が充実** — ServiceNow等は監査証跡の管理が得意

### パターン2のデメリット

- **カスタムアクションの開発が必要** — Scaffolderと外部システム間のインテグレーション開発コスト
- **システム間の整合性管理** — 外部システムの障害時やWebhook失敗時のリカバリ設計が必要
- **利用者の体験が分断される** — 申請はRHDH、承認状況の確認はServiceNow、と画面が分かれる
- **外部システムのライセンスコスト** — ServiceNow等は追加のライセンスが必要な場合がある

### パターン2が適するケース

- 既にServiceNowやJiraで承認フローが運用されている
- 承認者が非エンジニア（マネージャー、セキュリティ担当等）
- 組織のコンプライアンス要件で特定の承認システムの利用が義務付けられている
- 複雑な承認ルール（金額別承認者、部門別フロー等）が必要

## パターン3：RHDH Orchestratorプラグイン（ServerlessWorkflow）

### パターン3の概要

RHDH 1.7以降で利用可能なOrchestratorプラグインを使い、ServerlessWorkflow（SonataFlow）ベースの長時間実行ワークフローとして承認を含むフローを定義するパターンです。

### パターン3のフロー

![パターン3：RHDH Orchestrator](https://github.com/umemasa3/qiita-content/blob/main/public/images/rhdh-pattern3-orchestrator.drawio.svg?raw=true)

### パターン3の実装ポイント

- OpenShift Serverless Logic（SonataFlow）のインフラが必要
- ワークフロー定義はServerlessWorkflow仕様（YAML/JSON）で記述
- 承認待ちのステートはイベント待機またはコールバックとして実装
- RHDH Notificationsプラグインとの連携で承認者への通知が可能

### パターン3のメリット

- **RHDH内で完結する** — 申請も承認も状況確認もすべてRHDH上で行える
- **長時間実行ワークフローに対応** — 承認待ちで数日かかっても問題ない
- **リトライ・エラーハンドリングが標準機能** — ワークフローエンジンとしての堅牢性
- **イベント駆動で柔軟** — 外部イベントとの連携も可能
- **Red Hatのサポートを受けられる** — エンタープライズサポートがある

### パターン3のデメリット

- **インフラの追加コストが大きい** — OpenShift Serverless Logic（KNative + SonataFlow）の構築・運用が必要
- **学習コストが高い** — ServerlessWorkflow仕様、SonataFlow、KNativeの知識が必要
- **まだ成熟途上** — RHDH Orchestratorは比較的新しく、情報やコミュニティの知見が少ない
- **OpenShift前提** — OpenShift環境がなければ利用できない

### パターン3が適するケース

- 既にOpenShift環境を運用している
- RHDH内ですべてのUXを完結させたい
- 承認だけでなく、複雑な分岐・リトライ・長時間実行が必要なワークフロー全般を扱いたい
- Red Hatのエンタープライズサポートを重視する

## パターン比較表

| 観点 | パターン1: GitOps PR | パターン2: 外部WF連携 | パターン3: Orchestrator |
|------|---------------------|---------------------|----------------------|
| 導入コスト | 低い | 中〜高 | 高い |
| カスタム開発 | 不要 | カスタムアクション必要 | ワークフロー定義必要 |
| 承認者のスキル要件 | Git操作が必要 | 既存ツールのUIで可 | RHDH UIで可 |
| 多段承認 | 困難 | 容易 | 可能 |
| 監査証跡 | Gitログ | 外部システム | ワークフロー履歴 |
| UXの一貫性 | △（RHDHとGit） | △（RHDHと外部システム） | ○（RHDH内完結） |
| 前提インフラ | Git + CI/CD | 外部WFシステム | OpenShift + SonataFlow |
| 成熟度 | 高い | 高い | 発展途上 |

## どのパターンを選ぶべきか

### 判断のフローチャート

![承認パターン選定フローチャート](https://github.com/umemasa3/qiita-content/blob/main/public/images/rhdh-approval-selection-flow.drawio.svg?raw=true)

1. **承認者はGitの操作に慣れているか？**
   - Yes → パターン1を第一候補に
   - No → 2へ

2. **既にServiceNow等の承認システムが組織にあるか？**
   - Yes → パターン2を第一候補に
   - No → 3へ

3. **OpenShift環境を運用しているか？**
   - Yes → パターン3を検討
   - No → パターン1をシンプルに始めるか、パターン2で軽量なWFツール（GitHub Actions + Issue Approve等）を検討

### 組み合わせも有効

実際には、組織内で一つのパターンに統一する必要はありません。

- **開発チーム向け**（承認者がエンジニア）→ パターン1
- **全社サービス**（承認者がマネージャー）→ パターン2
- **複雑なプロビジョニング**（多段承認＋自動チェック）→ パターン3

チームや作業の性質に応じて使い分け、IDPのフロントエンドとしてのRHDHは共通で使う、という構成が現実的です。

## まとめ

RHDH/Backstageには承認ステップのネイティブ機能はまだありませんが、「GitのPR Approve」「外部ワークフローシステム」「Orchestratorプラグイン」の3つのアプローチで承認付きセルフサービスを実現できます。

重要なのは、**承認の存在そのものではなく、「何を自動化し、どこに人の判断を残すか」の設計**です。Excel申請書と手作業の時代から、パラメータの入力と承認は人が行い、それ以外はすべて自動化する。このバランスがプラットフォームエンジニアリングの腕の見せどころではないでしょうか。

「完全セルフサービス」だけがIDPのゴールではありません。組織の実情に合った承認フローを設計し、段階的に自動化を進めていくことが、ミッションクリティカルな環境でのプラットフォームエンジニアリングの現実解だと考えています。
