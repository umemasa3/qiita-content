## はじめに

これまでのエンタープライズ向けKiro記事で、ガバナンスやCloud Sessionsの話をするたびに「統制は `.kiro/` で担保する」と繰り返し触れてきました。今回はその `.kiro/` の中身そのものに踏み込みます。

組織でKiroを展開するとき、`.kiro/` に何を入れ、どこまでを組織標準として揃えるべきか——これは意外と設計判断が要る問題です。何も揃えなければ各人・各チームがバラバラの前提でKiroを使うことになり、逆に何もかも標準で縛ると現場の柔軟性を奪います。

この記事では、`.kiro/` に入る各要素の性質とスコープを整理した上で、エンタープライズ企業として「どこまで標準化すべきか」を検討します。結論を先に言うと、**全部を一律に標準化するのではなく、要素ごとに標準化のレイヤーを分ける**のが現実的だと考えています。

参考: [Kiro Docs - Configuration scopes](https://kiro.dev/docs/configuration/) / [Steering](https://kiro.dev/docs/steering/)

## 標準化の力：『コンテナ物語』が教えてくれること

`.kiro/` の話に入る前に、標準化そのものについて、マルク・レビンソンの『コンテナ物語（The Box）』を紹介させてください。標準化の価値と難しさが、この本にはとても分かりやすく描かれています。

1956年、トラック業者だったマルコム・マクリーンが、58個のアルミ製の箱をタンカーに積んで運んだのが、コンテナ輸送の始まりでした。コンテナ自体は、溶接とリベットで組んだただの鉄の箱です。しかしこの「箱」が、物流とグローバル貿易を根本から変えました。この歴史から、標準化について3つの示唆が得られます。

**1つ目は、標準化したのは「中身」ではなく「箱のインターフェース」だったこと。** コンテナの本質は、中に何が入っていようと、船・トラック・鉄道が同じ規格で扱える点にあります。中身は自由なまま、外側の規格だけを揃えたからこそ、輸送手段の間をシームレスに移動できるようになりました。

**2つ目は、標準化が既存のやり方の抵抗にあったこと。** 海運会社は多額の設備投資リスクに懐疑的で、港湾労働組合は雇用の喪失を脅威と捉えました。実際、ニューヨークの港湾雇用は大きく減りました。標準化は技術の問題であると同時に、人と組織の問題でもあったのです。

**3つ目は、規格が1つに収斂して初めて真価が出たこと。** 各社がバラバラのサイズの箱を使っていては、相互運用できません。ほぼどのコンテナもどのトラック・鉄道・船で運べるようにする規格の交渉があって、はじめてコンテナは世界を変えました。

この3つは、そのまま `.kiro/` の標準化にも当てはまります。

- 揃えるべきは各人の書き方（中身）ではなく、「どこに何を置くか」「共通の前提は何か」という規格（インターフェース）
- 組織標準の押し付けは現場の抵抗を生む。価値を示しながら進める必要がある
- 部門ごとにバラバラの `.kiro/` では相互運用できない。組織で規格を揃えて初めて効く

この視点を頭に置いて、`.kiro/` の中身を見ていきます。

## .kiro/ に入るものと、その配置スコープ

まず前提の整理です。Kiroの設定は3つのスコープを持ちます。

- **Global（`~/.kiro/`）** — 個人の全プロジェクトに効く。IDE/CLIのみ（Web/Mobileでは読まれない）
- **Project（`.kiro/`）** — リポジトリにコミットされ、そのワークスペースに効く。IDE/CLI/Web/Mobileすべてで読まれる
- **Agent（`.kiro/agents/` または `~/.kiro/agents/`）** — エージェント単位

`.kiro/`（プロジェクトスコープ）に入る主な要素は以下です。

| 要素 | パス | 役割 |
|------|------|------|
| Steering | `.kiro/steering/` | コーディング規約・技術スタック・設計原則などの永続コンテキスト |
| Specs | `.kiro/specs/` | 機能ごとの要件・設計・タスクの仕様 |
| Custom agents | `.kiro/agents/` | 特化したエージェント定義 |
| Hooks | `.kiro/hooks/` | イベント駆動の自動アクション |
| Skills | `.kiro/skills/` | 再利用可能な手順パッケージ |
| MCP servers | `.kiro/settings/mcp.json` | 使用するMCPサーバー定義 |

:::note info
ここで重要なのは、**プロジェクトスコープ（`.kiro/`）だけがKiro WebやMobileでも読まれる**という点です。
クラウドセッションで組織標準を効かせたいなら、`~/.kiro/`（個人）ではなくリポジトリの `.kiro/` にコミットする必要があります。
:::

## スコープ間の競合はどう解決されるか

標準化を考える上で、同じ設定が複数スコープにあるときの優先順位を知っておく必要があります。

| 要素 | 優先順位（高→低） |
|------|------------------|
| MCP servers | Agent > Project > Global |
| Permissions | スコープに関わらず deny が勝つ（deny-overrides） |
| Custom agents | Project > Global（同名はプロジェクトが勝ち、警告） |
| Steering | 全スコープをマージ（上書きではない） |
| Skills | 全スコープをマージ |
| Hooks | 全スコープをマージ |

:::note warn
Steering・Skills・Hooksは「上書き」ではなく「全スコープをマージ」です。組織のglobal steeringと個人のsteeringが両方効くため、組織標準を敷いても個人が追加した指示は消えません。逆に言えば、組織標準で「絶対に守らせたい」ことがある場合、steeringだけでは不十分でPermissions（deny-overrides）やガバナンス設定と組み合わせる必要があります。
:::

## どこまで標準化すべきか：要素ごとに考える

ここからが本題です。要素ごとに「組織標準にすべき度合い」は違います。

### 標準化すべき（組織で揃える価値が高い）

- **セキュリティ・コンプライアンスのsteering** — 機密情報の扱い、入力バリデーション、禁止事項。全社共通で守らせたい規範
- **技術スタックの前提（`tech.md`）** — 承認済みライブラリ、非推奨ライブラリ。生成コードの土台を揃える
- **MCP許可リスト** — 使ってよいMCPサーバー。前回のガバナンス記事の通り、野放しはリスク

### プロジェクト/チーム単位で揃える（一律は避ける）

- **コーディング規約（`code-conventions.md`）** — 言語やフレームワークごとに違う。全社一律より、プロジェクトの実態に合わせる
- **プロジェクト構造（`structure.md`）** — リポジトリごとに固有
- **Specs** — 機能仕様なので当然プロジェクト固有（そもそもglobalに置けない）

### 個人裁量に任せてよい

- **個人の作業効率化Skills・Hooks** — 自分の手癖を助けるもの。組織で縛る必要はない
- **エディタ内の個人設定** — 生産性の問題であって統制の問題ではない

## 組織標準をどう配布するか

「組織標準のsteering」を全社に効かせる方法は2つあり、性質が違います。

### 方法1：リポジトリの `.kiro/` にコミットする

テンプレートリポジトリや各プロジェクトの `.kiro/` に、組織標準のsteeringやMCP許可リストをコミットする方法です。

- リポジトリと一緒にバージョン管理され、変更履歴が残る
- **Kiro Web/Mobile（クラウドセッション）でも効く**（プロジェクトスコープだから）
- PRレビューで変更を統制できる

### 方法2：global steering をMDM/グループポリシーで配布する

Kiroには「team steering」という考え方があり、組織共通のsteeringファイルを **MDMソリューションやグループポリシーで各PCの `~/.kiro/steering/` に配布**できます。

- 全プロジェクト横断で個人のマシンに効く
- ただし **IDE/CLIのみ**（Web/Mobileでは読まれない）
- 端末管理の仕組みに乗るので、配布・更新を一元管理できる

:::note info
2つの方法は排他ではなく、組み合わせるのが実際的です。「全社横断の規範」はMDMで `~/.kiro/steering/` に配布しつつ、「クラウドセッションでも効かせたい標準」や「リポジトリ固有の標準」は `.kiro/` にコミットする、という使い分けです。
:::

## 標準化しすぎの落とし穴

組織標準を整えるのは良いことですが、やりすぎると逆効果になります。検討時に意識したい点です。

- **steeringが肥大化するとコンテキストを圧迫する** — 「always」を増やしすぎると毎回の前提が膨らむ。`fileMatch` / `manual` / `auto` の inclusion mode で必要なときだけ読ませる
- **マージ仕様を誤解しない** — steeringは全スコープマージなので、組織標準を敷いても個人が上書きで無効化はできない。逆に「絶対禁止」はsteeringでは表現しきれない
- **現場の実態と乖離した標準は形骸化する** — 使われない標準はメンテされず、やがて誰も守らなくなる。標準は最小限から始めて育てる

:::note warn
steeringファイルはコードベースの一部です。APIキーやパスワードなどの機密情報を絶対に書き込まないでください。また、steeringの変更はコードと同じくレビュー対象にすることが推奨されています。
:::

## まとめ

`.kiro/` の標準化は「全部揃える」でも「何も揃えない」でもなく、**要素ごとにレイヤーを分ける**のが現実解だと考えます。

- `.kiro/`（プロジェクト）はWeb/Mobileでも読まれ、`~/.kiro/`（個人）はIDE/CLIのみ。クラウドセッションで効かせたいならリポジトリにコミットする
- Steering・Skills・Hooksは全スコープマージ。組織標準を敷いても個人の追加は消えない
- セキュリティ規範・技術スタック前提・MCP許可リストは組織標準にする価値が高い
- コーディング規約・構造・Specsはプロジェクト単位、個人効率化は裁量に任せる
- 組織標準の配布は、リポジトリ `.kiro/` へのコミットと、MDMによる `~/.kiro/steering/` 配布を使い分ける
- 標準化しすぎるとコンテキスト圧迫と形骸化を招く。最小限から始めて育てる

エンタープライズでKiroを展開するとき、最初から完璧な標準を作ろうとせず、「全社で絶対に守らせたい最小限」をまず `.kiro/` とガバナンス設定で固め、残りはプロジェクトと個人に委ねる。この線引きが、統制と柔軟性のバランスを取る鍵だと考えています。

コンテナが「中身は自由なまま、箱の規格だけを揃えた」ように、`.kiro/` の標準化も中身の書き方まで縛るのではなく、揃えるべきインターフェースだけを最小限に規格化する。そこから育てていくのが、抵抗を生まず効果を出す進め方だと考えています。
