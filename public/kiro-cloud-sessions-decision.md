## はじめに

これまでエンタープライズでKiroを使う際のデータ保護、プロンプトログ、マルチアカウントのガバナンスを整理してきました。今回はもう一つの判断ポイント、**Kiro Web（Cloud Sessions）を組織で有効化すべきか**についてです。

Cloud Sessionsは、Kiroのエージェントを自分のマシンではなく**Kiroのマネージドクラウドサンドボックス**で動かす機能です。ブラウザやスマホから長時間タスクを投げて、ラップトップを閉じても裏でエージェントが働き続ける——という便利さがあります。

一方で、IAM Identity Centerを使う組織ではCloud Sessionsは**デフォルトで無効**になっており、管理者が明示的に有効化しないと使えません。これは「便利だから開けておく」機能ではなく、**有効化の是非を判断すべき機能**だということです。

この記事では、Cloud Sessionsの仕組みと、組織で有効化すべきかどうかの判断材料を整理します。

参考: [Kiro Docs - Cloud sessions](https://kiro.dev/docs/cloud-sessions/) / [AWS Identity Center](https://kiro.dev/docs/web/identity-center/)

## Cloud Sessionsで何がどこで動くのか

判断の前に、まず「何がどこで実行されるか」を正確に押さえます。ここがローカルのIDE/CLIと決定的に違う点です。

Cloud Sessionを作成すると、Kiroが隔離されたサンドボックスをプロビジョニングし、ローカルと同じエージェントハーネスを起動します。そこで起きることは次の通りです。

- **リポジトリはサーバー側でclone** — 接続したGitHub/GitLab経由でKiroがサーバー側でcloneする。ローカルの作業コピーはアップロードされない
- **ファイルの読み書き・シェルコマンド・ビルドはすべてサンドボックス内で実行** — ローカルマシンでは動かない
- **結果は接続元プロバイダ経由（多くはPR）または会話で返る**
- **セッションはクラウド側に永続** — 会話履歴・バインドしたリポジトリ・サンドボックスのファイル状態が残り、どの端末からでも再接続できる

つまり、Cloud Sessionsは「あなたのコードをKiroのクラウド環境でcloneして、そこでエージェントが自律的に動く」仕組みです。ローカル完結のIDE/CLIとはセキュリティ境界が根本的に違います。

## 判断材料1：管理者のガバナンス設定が効かない

ここが組織にとって最も重要な判断材料です。前回のガバナンス記事で触れた管理者設定のうち、**いくつかはKiro Webセッションには適用されません**。

公式ドキュメントに明記されている、Kiro Webに効かない共有設定は以下です。

- Include suggestions with code references（コード参照情報の付与）
- Model Context Protocol（MCP）
- Model availability（使えるモデルの制限）
- Member account subscriptions
- MCP registry URL（MCP許可リスト）
- Encryption key — カスタマーマネージドキー（CMK）はKiro Webでは非対応

さらに、モデル選択やWeb tool制御といった他のガバナンスポリシーも、現状Kiro Webには提供されていません。

:::note alert
IDEやCLIで効かせているMCP制限・モデル制限・CMKによる暗号化などの管理者ガバナンスは、Kiro Web（Cloud Sessions）には適用されません。IDE/CLIを厳しく統制していても、Cloud Sessionsを有効化するとその統制の外で開発が行われる経路が開くことになります。
:::

ミッションクリティカルなシステムを抱え、MCPやモデルを組織ポリシーで統制している組織にとって、これは看過できない差です。「IDE/CLIはガチガチに固めたのに、Cloud Sessionsから統制外のMCPが使えてしまう」という抜け穴になりかねません。

## 判断材料2：Supervisedモードが使えない（自律実行前提）

Cloud Sessionsは **Autopilot** または **Autonomous** で動きます。変更ごとに人が承認する **Supervisedモードは現状使えません**。

ローカルのIDEでは変更を1つずつ確認しながら進められますが、Cloud Sessionsではエージェントがサンドボックス内で自律的にファイルを編集し、シェルコマンドを実行し、ビルドを走らせます。結果はPRとして返るため最終レビューはできますが、**実行途中の一手ずつを止める運用はできない**という前提を理解しておく必要があります。

:::note warn
Cloud SessionsはAutopilot/Autonomousのみで、変更ごとの承認（Supervisedモード）はできません。エージェントがサンドボックス内で自律的にコマンドを実行することを許容できるかが判断の分かれ目です。
:::

## 判断材料3：実行リージョンと同時実行数の制約

プレビュー段階特有の制約もあります。

- **実行リージョンは us-east-1（バージニア北部）のみ** — プレビュー中はここに固定。データの処理場所に制約がある組織は要確認
- **同時実行は最大10セッション**
- **リポジトリはセッション作成時に固定**（後からブランチ選択も不可。起動後にエージェントへ指示してチェックアウトさせる）

:::note warn
プレビュー中、Cloud Sessionsの実行環境は us-east-1 に固定されます。データの国内処理など地理的な要件がある組織では、この点が制約になります。
:::

## 判断材料4：設定の届き方が変わる

Cloud Sessionsでは設定の適用範囲も変わります。

- **プロジェクト設定（リポジトリ内の `.kiro/`）** — steering、spec、カスタムエージェント、hook、MCPサーバー定義はリポジトリのcloneとともにサンドボックスに届く
- **個人設定（`~/.kiro/`）** — 自動適用されない。持ち込むにはKiro Webの設定画面から同期する必要がある

プロジェクトにコミットされた `.kiro/` は効くが、ローカルの個人設定は自動では効かない、という違いです。チーム標準を `.kiro/` でリポジトリに入れておく運用が、Cloud Sessionsでは特に効いてきます。

## 有効化すべきかの判断フロー

以上を踏まえた判断の流れを整理します。

![Kiro Web（Cloud Sessions）を有効化すべきかの判断フロー](https://github.com/umemasa3/qiita-content/blob/main/public/images/kiro-cloud-sessions-decision.drawio.svg?raw=true)

### 有効化を前向きに検討できるケース

- コードが既にGitHub/GitLabにあり、サーバー側cloneが許容できる
- 統制はプロジェクトの `.kiro/`（コミット済み設定）とPRレビューで担保する方針
- 長時間タスクや、端末を離れても走り続ける自律実行の価値が大きい
- us-east-1でのデータ処理が要件上問題ない

### 有効化に慎重になるべきケース

- MCP・モデル・CMKを組織ポリシーで厳格に統制している（Cloud Sessionsには効かない）
- 変更ごとの承認（Supervised）が運用上必須
- データの処理場所に地理的制約がある
- 自律実行のサンドボックスに自社コードを置くこと自体に懸念がある

## 有効化する場合に決めておくべきこと

有効化すると決めた場合、以下を整理してから開けることをおすすめします。

- **どのリポジトリを対象にするか** — サーバー側cloneされる対象を明確にし、機密度の高いリポジトリを含めるか判断する
- **`.kiro/` による統制の整備** — MCPやモデルの組織ガバナンスが効かない分、プロジェクトの `.kiro/` にsteeringや許可するMCPを定義してリポジトリ側で担保する
- **PRレビューのゲート** — Supervisedが使えないため、サンドボックスの成果物はPRで必ずレビューする運用を敷く
- **利用者への周知** — コードがKiroのクラウドサンドボックスでcloneされ実行されること、IDE/CLIの管理者統制が一部効かないことを説明する

## まとめ

Kiro Web（Cloud Sessions）は、エージェントをKiroのマネージドサンドボックスで自律的に動かす強力な機能です。ただしIAM Identity Center組織ではデフォルト無効で、有効化は組織としての判断を要します。

- Cloud Sessionsはリポジトリをサーバー側でcloneし、ファイル操作・ビルド・シェル実行をサンドボックス内で行う
- MCP・モデル・CMKなどの管理者ガバナンスがKiro Webには適用されない
- Supervisedモードは使えず、Autopilot/Autonomousの自律実行が前提
- プレビュー中は us-east-1 固定、同時10セッションまで
- プロジェクトの `.kiro/` は効くが個人設定は自動では効かない

便利さの裏で、IDE/CLIで固めた統制の外に開発経路が広がる、という点が最大の判断材料です。ミッションクリティカルな環境ほど、「有効化すると何が統制外になるか」を洗い出し、`.kiro/` とPRレビューで代替の統制を用意してから開ける、という順序が安全だと考えています。デフォルトで無効になっているのは、まさにそれだけ慎重な判断を求められる機能だからです。
