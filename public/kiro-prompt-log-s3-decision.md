## はじめに

前回の記事で、エンタープライズユーザーとしてKiroを使えば、入力したコードやプロンプトがモデル学習に使われないことを整理しました。

参考: [エンタープライズでKiroを使うなら、ログイン方法でデータの扱いが変わる](https://qiita.com/umemasa3/items/57f3b2c90a14164c3053)

今回はその次のステップの話です。Kiroには、エンタープライズ管理者が組織内の利用状況を把握するための仕組みがいくつか用意されています。その中でも「プロンプトログのS3出力」は、有効にするかどうかを慎重に判断すべき機能です。

というのも、プロンプトログを有効にすると、**開発者がKiroに入力したプロンプトとKiroの応答、さらにインライン補完で受け入れたコードまで、すべて自社のS3バケットに記録される**からです。監査やコンプライアンスの観点では有用ですが、開発者の入力内容が丸ごと残るということでもあります。

この記事では、Kiroが提供する監視機能を整理した上で、プロンプトログをS3に出力すべきかどうかの判断基準をまとめます。

参考: [Kiro Docs - Logging user prompts](https://kiro.dev/docs/enterprise/monitor-and-track/prompt-logging/)

## Kiroが提供する3つの監視機能

Kiroのエンタープライズ機能には、性質の異なる3つの監視・記録手段があります。

- **ダッシュボード** — Kiroサブスクライバーの利用状況を集計したメトリクスを表示する。全体傾向の把握向け
- **ユーザーアクティビティレポート** — 個々のユーザーがKiroで何をしているかを示すレポート
- **プロンプトログ** — IDEやCLIで入力された全プロンプトとKiroの応答を記録し、自社のS3バケットに保存する

この3つは「粒度」と「保存されるデータの重さ」が大きく違います。ダッシュボードとレポートは集計・メタデータ寄りですが、プロンプトログは**入力そのもの（コードやプロンプト本文）を保存する**点が決定的に異なります。

これらの機能は、Kiroの設定画面（Kiro console）から有効化します。実際の設定画面では、「使用アクティビティ」のセクションに使用状況ダッシュボードやユーザーアクティビティレポートのトグルが並んでいます。

![Kiroの設定画面（使用アクティビティのセクション）](https://github.com/umemasa3/qiita-content/blob/main/public/images/kiro-settings-usage-activity.png?raw=true)

ユーザーアクティビティレポートの説明に「create daily reports in an S3 bucket」とあるように、レポート系の機能もS3バケットへの出力を伴う点は共通しています。

## プロンプトログで実際に保存される内容

プロンプトログを有効にすると、何が記録されるのかを具体的に見てみます。公式ドキュメントのログ例をもとに整理します。

チャットの場合、以下のような内容が記録されます。

- `prompt` — ユーザーがチャットに入力したプロンプト本文
- `assistantResponse` — Kiroが返した応答
- `userId` — 入力したユーザーのID
- `timeStamp` — 入力日時（UTC）
- `conversationId` — 会話をグループ化するID

インライン補完の場合は、さらに踏み込んだ内容が保存されます。

- `leftContext` — カーソル前のコード（コンテキストとして使われた部分）
- `rightContext` — カーソル後のコード
- `fileName` — 補完が要求されたファイル名
- `completions` — Kiroが提案しユーザーが受け入れたコード

つまり、**開発中のソースコードの断片やファイル名まで平文でS3に残る**ということです。ここが判断の肝になります。

:::note alert
プロンプトログを有効にすると、開発者のプロンプト本文と、インライン補完で扱われたソースコードの断片が平文でS3に蓄積されます。このバケットの漏洩は全開発者のコード漏洩に等しいため、保存すること自体のリスクを理解した上で判断してください。
:::

## 出力先とコスト

保存先とコストの前提も押さえておきます。

- ログは**自社のAWSアカウント内のS3バケット**に保存される（Kiro側ではなく自分の管理下）
- バケットはKiroプロファイルと同じリージョン・同じアカウントである必要がある
- バケットには専用のバケットポリシー（`q.amazonaws.com` からの `s3:PutObject` を許可）が必要
- 費用はS3のストレージ代と、暗号化にKMSキーを使う場合の少額の手数料のみ。機能自体は無料

自社アカウント内に保存されるという点は重要です。データが外部に出るわけではなく、あくまで自組織の管理下に置かれます。

:::note info
プロンプトログ機能自体は無料で、かかるのはS3のストレージ代と、暗号化にKMSキーを使う場合の少額の手数料のみです。
:::

## プロンプトログをS3出力すべきかの判断基準

以上を踏まえて、プロンプトログをS3に出力すべきかを判断する観点を整理します。

### 出力を検討すべきケース

- **規制業界でコンプライアンス要件がある** — 金融、医療、公共など、開発活動の監査証跡を残す義務がある場合
- **インシデント対応で追跡可能性が必要** — 「誰がどんな指示でどんなコードを生成したか」を後から追える状態にしたい
- **AIの利用実態を分析したい** — どんなプロンプトが多いか、生成コードの傾向を把握して教育やガバナンスに活かす
- **セキュリティ調査の証跡が必要** — 機密情報がプロンプトに含まれていないかの事後確認をしたい

### 出力に慎重になるべきケース

- **開発者のプライバシーへの配慮が必要** — 全プロンプト・全コードが記録されることを開発者が認識しているか。監視されている感覚が生産性や心理的安全性を下げないか
- **保存されるログ自体が新たな機密情報になる** — ソースコードやプロンプトが平文で蓄積されるS3バケットは、それ自体が高い保護を要する資産になる。バケットの漏洩は全開発者のコード漏洩に等しい
- **ログの活用体制がない** — 出力するだけで誰も見ない、分析もしないなら、リスクだけが増えて価値が生まれない
- **保持ポリシーが決まっていない** — ログを無期限に貯め続けると、ストレージコストと漏洩時の被害範囲が際限なく膨らむ

### 判断のフローチャート

## ユーザーアクティビティレポートは判断基準が違う

ここまではプロンプトログの話でしたが、同じくS3に出力される「ユーザーアクティビティレポート」は、判断基準が大きく異なります。両者を混同すると判断を誤るので、分けて考える必要があります。

ユーザーアクティビティレポートは、毎日UTC 2:00にクライアント種別（IDE / CLI / Plugin）ごとのCSVを自社のS3バケットに出力する機能です。含まれるのは以下のような**メトリクス**です。

- `Date` / `UserId` / `User_Email` — 日付とユーザー識別情報
- `Client_Type` — KIRO_IDE / KIRO_CLI / PLUGIN
- `Chat_Conversations` — その日の会話数
- `Credits_Used` / `Overage_Credits_Used` — クレジット消費量
- `Total_Messages` — Kiroとやり取りしたメッセージ数
- `Subscription_Tier` — 契約プラン
- モデル別のメッセージ数

ここで決定的に重要なのは、**ユーザーアクティビティレポートにはプロンプト本文やソースコードが含まれない**という点です。あくまで「誰が・どれくらい・何を使ったか」という利用量のメトリクスであり、入力内容そのものは記録されません。

この違いから、判断のハードルは大きく変わります。

- **プロンプトログ** — 入力本文・コードが平文で残る。ログ自体が機密資産になるため、慎重な判断が必要
- **ユーザーアクティビティレポート** — メトリクスのみ。漏洩時のリスクはプロンプトログより格段に低い

:::note info
ユーザーアクティビティレポートはプロンプト本文やコードを含まないため、プロンプトログより判断のハードルは低く、多くの組織で有効化して問題ありません。
:::

そのため、ユーザーアクティビティレポートは**多くの組織で有効化して問題ない**と考えられます。むしろ以下の目的では積極的に活用する価値があります。

- **ライセンス最適化** — 使っていないユーザーの洗い出し、プランの適正化
- **クレジット・オーバーエイジ消費の把握** — コスト管理
- **利用実態の可視化** — Athenaでクエリ、QuickSightで可視化して定着度を測る

### Amazon Q Developerからの移行で特に効いてくる

このレポートの重要性は、Amazon Q Developerから移行した組織で特に実感します。

Amazon Q Developerのユーザー管理画面では、各ユーザーの**最終ログイン日**が一覧で確認できました。誰がしばらく使っていないかが一目で分かるため、「3ヶ月ログインしていないユーザーのライセンスを剥がす」といったライセンス最適化が簡単にできていました。

ところがKiroに移行すると、この最終ログイン日が管理画面から把握しづらくなっています。使われていないライセンスを見つける手軽な手段がなくなってしまうわけです。

ここでユーザーアクティビティレポートが効いてきます。日次のCSVには `Date` `UserId` `Chat_Conversations` `Total_Messages` といったメトリクスが含まれるため、これをAthena等で集計すれば「直近N日間アクティビティがゼロのユーザー」を抽出できます。最終ログイン日の代わりに、**アクティビティの有無からライセンスの棚卸しができる**わけです。

Q Developerでは管理画面のワンクリックで済んでいたことが、Kiroではレポートを出力して集計する一手間が必要になった、という理解です。だからこそ、移行組にとってこのレポートの有効化は「あると便利」ではなく「ライセンス管理のために実質必須」に近い位置づけになります。

ただし、`User_Email` などの個人を特定できる情報が含まれるため、レポートを見られる人の範囲は限定すべきです。また、CSVとはいえS3バケットの保護（暗号化、パブリックアクセスブロック、最小権限のバケットポリシー）はプロンプトログと同様に必要です。

:::note warn
ユーザーアクティビティレポートには `User_Email` などのPIIが含まれます。閲覧できる人を限定し、S3バケットの保護（暗号化・パブリックアクセスブロック・最小権限ポリシー）は必ず設定してください。
:::

なお、実装上の注意点として、ユーザーアクティビティレポート用のバケットはプロンプトログ用とは**別のバケットにすることが推奨**されています（用途と保護レベルが異なるため）。

## 出力する場合に決めておくべきこと

出力すると決めた場合、有効化する前に以下を設計しておくことをおすすめします。

- **バケットの保護** — バケットポリシーの最小権限化、KMSによる暗号化、パブリックアクセスブロック、アクセスログの取得
- **保持期間** — ライフサイクルポリシーで古いログを自動削除する。監査要件で必要な期間だけ保持する
- **アクセス制御** — ログを閲覧できる人を限定する。開発者本人のコードを誰が見られるのかを明確にする
- **開発者への周知** — プロンプトとコードが記録されることを事前に説明し、合意を取る。黙って監視するのは信頼を損なう
- **活用プロセス** — 誰が・いつ・何のためにログを見るのかを決める。目的のない収集は避ける

## まとめ

Kiroのプロンプトログは、開発者の入力とKiroの応答、そして生成・補完されたコードまでを自社のS3バケットに記録する機能です。監査やコンプライアンスには有用ですが、保存されるログ自体が機密情報の塊になるという裏返しがあります。

- ダッシュボードやユーザーアクティビティレポートは集計・メタデータ寄り、プロンプトログは入力本文まで保存する点が決定的に違う
- ログは自社アカウント内のS3に保存され、費用はストレージ代程度
- 規制・監査・インシデント対応の要件があるなら出力を検討する価値がある
- 一方で、開発者のプライバシー、ログ自体の保護、保持ポリシー、活用体制が伴わないなら、リスクだけが増える
- ユーザーアクティビティレポートはメトリクスのみでプロンプト本文を含まないため、多くの組織で有効化して問題なく、ライセンス最適化やコスト管理に有用
- 特にAmazon Q Developerから移行した組織では、最終ログイン日が管理画面で見えなくなったため、レポートのアクティビティ集計がライセンス棚卸しの実質的な代替手段になる

大事なのは、S3に出力する機能を一括りにせず、**「メトリクスだけのユーザーアクティビティレポート」と「入力本文まで残すプロンプトログ」を分けて判断する**ことです。前者は積極的に活用してよく、後者は目的・保護・保持・周知をセットで設計してから有効化する。この線引きが、エンタープライズでKiroを運用する上での勘所だと考えています。
